## Database Engine

The project uses **Drizzle ORM** with **dual-mode support**:

| Mode        | Engine                  | When                                  |
| ----------- | ----------------------- | ------------------------------------- |
| Development | **SQLite** (file-based) | Default — zero-setup, fast iteration  |
| Production  | **PostgreSQL 16+**      | Recommended for multi-user production |

The schema is defined once in `database/src/schema/index.ts` and Drizzle generates dialect-appropriate SQL.

### Connection

- Config: `backend/src/config/database.config.ts`
- Env:
  ```bash
  DATABASE_PROVIDER=sqlite          # sqlite | postgresql
  DATABASE_URL=file:./data/dev.db   # sqlite
  # DATABASE_URL=postgresql://user:pass@host:5432/db  # postgresql
  ```

> **Note on dev databases:** `*.db` files are **gitignored** — never commit them. Each developer generates their own local DB via migrations + seeds.

## Conventions

- **Naming:** tables & columns `snake_case`
- **Primary keys:** text/UUID ids (`id`)
- **Timestamps:** `created_at`, `updated_at`
- **Soft delete:** `deleted_at`, `is_deleted` on business tables
- **Audit:** `created_by`, `updated_by` where applicable; full audit trail via `shranix_audit_details`
- **Money:** `real` (SQLite) / `numeric` (PostgreSQL) for amounts; tax fields `cgst/sgst/igst/cess`

## Migrations

Migrations are generated by Drizzle Kit and stored in `database/src/migrations/` as SQL files + a `meta/` journal.

### Commands

```bash
# 1. Modify the schema in database/src/schema/*.ts
# 2. Generate the migration SQL:
pnpm db:generate

# 3. Apply pending migrations:
pnpm db:migrate
```

### Inside Docker

The runner image is a minimal Node runtime — the migration tooling (drizzle-kit) lives in the repo's `database/` workspace, not in the container. Apply migrations from a machine with the repo checked out, pointing at the deployed database:

```bash
DATABASE_URL=postgresql://user:pass@host:5432/shranix_erp pnpm db:migrate
```

Run this as a deployment step (CI or the deploy host) before the backend scales up.

### Migration workflow rules

- One migration per logical change; review the generated SQL before applying.
- Never edit an already-applied migration (the journal tracks hashes) — create a new one.
- Migration files + journal are committed to git (schema is source of truth for new environments).

## Seed Process

Seeding is **idempotent** and safe to re-run (`database/src/seeds/run.ts`).

```bash
pnpm db:seed
```

What gets seeded:

- **Admin user** — `admin@shranix.com` / `admin123` (dev only — change in production!)
- **Roles & permissions** — core RBAC roles + permission sets
- **Master data** — companies, branches, warehouses, units, tax groups, GST rates, chart of accounts groups
- **Dummy business data** — sample customers, suppliers, items, price lists (for demos/testing)
- **Approval matrices** — default workflow matrices (e.g. 3-level sales quotation approval)

> The seed only creates what's missing; it never wipes existing data.

## Backup & Restore

The backup script targets **PostgreSQL** (production).

```bash
# Backup (pg_dump, gzip, integrity verify, 30-day retention)
./scripts/backup.sh backup

# List backups
./scripts/backup.sh list

# Restore
./scripts/backup.sh restore --file=<backup-file>

# Cleanup old backups
./scripts/backup.sh cleanup
```

Scheduled daily backups:

```bash
# Add to crontab (example — 2 AM daily)
0 2 * * * /path/to/scripts/schedule-backup.sh >> /var/log/shranix-backup.log 2>&1
```

For **SQLite** dev databases, the same script's `VACUUM INTO` snapshot path can be used (`scripts/check-db.mjs` shows the pattern). Backups are never committed (`.gitignore` excludes `**/backups/*.db`).

## ORM Commands (Drizzle)

| Command              | Purpose                                            |
| -------------------- | -------------------------------------------------- |
| `pnpm db:generate`   | Generate a migration from schema changes           |
| `pnpm db:migrate`    | Apply pending migrations                           |
| `pnpm db:push`       | Push schema directly (dev, no migration files)     |
| `pnpm db:push:force` | Force-push schema (dev, drops conflicting objects) |
| `pnpm db:studio`     | Open Drizzle Studio GUI                            |
| `pnpm db:seed`       | Seed the database                                  |
| `pnpm db:rollback`   | Manual guidance (revert SQL + re-migrate)          |

> Use `db:push` only on disposable dev databases. For anything with real data, prefer migrations.

## Troubleshooting

### "table already exists" during migrate

The journal thinks a migration ran but the table wasn't created (e.g. partially-applied). On a disposable dev DB: `rm data/dev.db && pnpm db:migrate && pnpm db:seed`.

### Backend connects to the wrong DB

Check which `.env` is loaded and confirm `DATABASE_URL` is absolute or resolves from the correct workspace directory. The config module resolves env files from the repository root.

### Column missing after pulling latest code

Run `pnpm db:migrate` — the latest migration adds it.
